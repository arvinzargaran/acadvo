# Security

Acadvo holds transcripts, grades, and career plans for individual students. A
breach here is not an inconvenience — it is academic records attached to real
names. This file says who is responsible, how to report a problem, and what
happens when something goes wrong.

## Reporting a vulnerability

Email the security owner above. Please **do not** open a public GitHub issue for
anything exploitable.

Include what you did, what you saw, and roughly when. A proof-of-concept helps.
You will get an acknowledgement within 72 hours.

Please do not access, modify, or retain another person's data while testing. If
you reach real student data by accident, stop, say so in the report, and delete
your copy — that is treated as good-faith disclosure, not as the finding itself.

## What is in scope

The deployed application, its API, and the container images in this repository.
Out of scope: findings that require a compromised student device, social
engineering of the operator, denial of service by raw volume, and reports
generated by a scanner with no demonstrated impact.

## Incident response

**1. Contain.** Take the affected path out of service before diagnosing it.
Suspending a feature is reversible; leaking for another hour while you read logs
is not.

```bash
docker compose -f docker-compose.prod.yml stop backend   # hard stop
```

**2. Revoke.** Rotate anything that may have been exposed, in this order — each
is independent, so do not wait on the previous one:

| Secret | Where | Effect of rotating |
|---|---|---|
| `JWT_SECRET_KEY` | `.env` | Signs out **every** user immediately. Use this when session theft is suspected. |
| `GROQ_API_KEY` | `.env` + Groq console | AI features fail until replaced. No user data is at risk through this key, but a leaked key is someone else's bill. |
| `POSTGRES_PASSWORD` | `.env` + database | Requires a coordinated restart of db + backend. |
| SMTP credentials | `.env` + mail provider | Password-reset and verification mail stops until replaced. |

Rotating `JWT_SECRET_KEY` is the single highest-value action in a suspected
account-compromise incident, and it is one edit plus a restart.

**3. Assess.** Before writing to anyone, answer in writing: what data, whose,
how many, over what window, and how you know. The structured logs carry a
request id on every line (`app/observability.py`) — that is the thread to pull.

**4. Notify.** Canadian institutions fall under PIPEDA: a breach creating a *real
risk of significant harm* must be reported to the Privacy Commissioner and to
affected individuals **as soon as feasible**. Academic records plus identity
details clear that bar easily. Tell people what happened, what you did, and what
they should do — before they read it somewhere else.

**5. Write it up.** Blameless, and specific: what broke, why it was possible, why
nothing caught it, and the one change that would have. A postmortem that ends in
"be more careful" has not found the cause.

## What we promise users about their data

The published [privacy policy](frontend/src/pages/PrivacyPage.jsx) is a set of
commitments a breach response has to honour, not marketing copy. Three of them
bind directly on an incident:

- **Breach notification.** A breach creating a real risk of significant harm is
  reported to affected users and to the Privacy Commissioner — the policy says so
  in section 6, which means the notification duty below is now also a promise.
- **Uploaded documents are never stored.** Transcripts and résumés are parsed in
  memory and dropped. If that ever changes, the policy becomes false and has to
  change in the same commit.
- **Access and deletion are self-serve.** `GET /users/me/export` and
  `DELETE /users/me` must keep working; an outage in either is a compliance
  incident, not just a broken feature.

The policy also states that "every endpoint is rate-limited". That is **not**
what the code does: 23 of the 85 API routes carry an explicit
`@limiter.limit`, and `app/limiter.py` sets no `default_limits`, so the rest are
unlimited per-IP. Either the page is corrected or a default limit is applied —
an inaccurate security claim in a published policy is the kind of thing a
regulator reads back to you.

## Recovery

Backups, restore, and rollback are documented in
[README.md](README.md#backups-restore-and-rollback). Two properties that are only
real if you have tested them — do it on a scratch host, before you need them:

- `./scripts/restore-db.sh <dump>` actually restores.
- You can roll back to the previous image and it still boots.

## What is already enforced

So that a review starts from what exists rather than from zero:

| Control | Where |
|---|---|
| Refuses to boot on unsafe production config (weak JWT secret, wildcard CORS, insecure cookies, no SMTP) | `app/main.py` lifespan |
| Auth: JWT HS256 with algorithm allowlist, refresh-token rotation, bcrypt | `app/services/auth.py`, `app/config.py` |
| CSRF via a header browsers cannot forge cross-origin | `app/main.py` `csrf_protection` |
| Per-route rate limits, shared across workers via Redis in production | `app/limiter.py`, `docker-compose.prod.yml` |
| SSRF: URL validated as a string, then re-checked against the resolved IP on every redirect hop | `app/research/schema.py`, `app/ai/research_client.py` |
| Prompt injection and model-output containment | `app/ai/sanitize.py`, `tests/test_prompt_injection.py` |
| Cross-user access denial | `tests/test_cross_user_access.py` |
| Secret scanning (full history), SAST (CodeQL + Bandit), dependency audit (pip-audit + npm audit) | `.github/workflows/ci.yml` |
| Container hardening: non-root, `cap_drop: ALL`, `no-new-privileges`, read-only rootfs | `docker-compose.prod.yml`, `backend/Dockerfile` |
| Readiness gate that fails closed when the database is unreachable | `app/main.py` `/health/ready` |
| Account deletion (password-confirmed, cascades to all user data) | `app/routers/users.py` |

## Known accepted risks

- **Rate limits are per-process without Redis.** The production compose sets
  `RATE_LIMIT_STORAGE_URI`; any other deployment shape must, or limits multiply
  by the worker count.
- **Requirement rules are model-extracted.** They carry a citation and a
  `stated`/`inferred` basis, and they can never introduce a course into the
  catalog — but they are not a substitute for an official degree audit, and the
  UI says so.
